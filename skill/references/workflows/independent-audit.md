# 独立验收专项流程

本流程只适用于已授权的独立验收。所有验收优先由 Codex 从可复用验收 Project 池中选择 C2C 路线：每个同时进行的独立验收独占不同的 project-only Project、新 Chat 和精确候选，跨任务不得共用活跃 Project。完成完整留证，并核实会话及业务材料已移出/归档后，Project 才可复用；池按实际验收并发调整，不按业务项目总数增长，不设无依据固定上限。池空位不足或独占、清理、项目记忆/上下文隔离及只读边界无法核实时，改走“冻结证据包 + 原生附件”的临时不个性化路线，不强制排队。规划讨论继续沿用已核验的规划绑定，不能把规划窗口的自查称为独立审核。

## 临时附件补位路线

1. 只有池空位、独占、清理或隔离无法核实时才新建临时普通 Chat；在实际界面核实“不个性化”已选中，且说明不使用记忆、插件和自定义指令。仅有临时 URL 或新窗口不足以证明隔离。它不是项目共享入口，不加入跨项目记忆池。首条消息必须包含完整的只读审核规则、冻结证据包索引、实际任务与结论格式。
2. 发送首条消息前，按 `browser.md` 的“模型与思考档位”读取当前输入区真实型号和强度。默认使用 GPT-5.6 Sol Pro；由 Codex 按当前全局规则及浏览器流程的推理收益判断选择 GPT-6 Pro，GPT-6 Pro 回复处理完立即回切 GPT-5.6 Sol Pro。消息文字不能切换网页模型。
3. Codex 自动冻结必要材料：原始用户意图、授权范围、规格和验收标准、精确候选、依赖、差异、真实测试输出、文件 manifest 与 SHA-256 清单，并记录实际 owner、任务、`auditRun`、轮次、候选 SHA 和 manifest SHA。若使用聚合候选 SHA，必须同时附候选文件集合，以及确定的排序、规范化和哈希算法，使独立审核者可以重算。原生附件只上传原件和索引，不把正文粘进控制消息或普通 Chat 正文。
4. 审核者可以要求补证；Codex 自动补齐并重新冻结。材料缺失、附件正文或读取完整度无法核实，结论只能是“需补证”或“独立审核未完成”，不得给候选“通过”。候选、输入或标准发生变化时，旧结论和绑定立即失效，必须重新冻结并验收。
5. 临时 URL 若不含可核验的 `/c/`，不得猜造会话 ID，不写入维护入口的
   `node "<ACTUAL_CHECKOUT_PATH>/dist/cli/index.js" session ... --role audit`，
   也不创建持久 role 绑定。审核记录不得点“保存成普通聊天”，不得用自动删除代替隔离；在完整记录核验落盘前不得关闭临时窗口。
   临时 URL 不是唯一身份；同时记录当次浏览器及实际标签标识、完整 Codex owner 和 auditRun。恢复时重新核验，标签丢失则依据已保存记录新开补审，不冒认其他临时聊天。
6. 保存到源项目认可存储的完整记录至少包括：实际提示词、附件原件、完整可见问答和报告、输入区模型/强度与回复模型证据、冻结元数据、补证记录和最终结论。`content.export` 未受支持时，用当前受支持的 DOM 读取完整可见正文后本地留存；不得把失败或未调用的导出说成成功。上传成功或看到哈希只证明传输/标识，不能证明附件全文已读取；必须实际读取并核实完整度。
7. 审核者只读冻结材料，不修改候选。审核者可以针对冻结候选给出“通过”“需修正”或“阻断”结论，但不能把自身参与形成的工作包当作独立审核，也不能给自己的实现自发 PASS。隔离、只读或材料完整性无法证明时，报告普通复核或独立审核未完成。

## C2C Project 池验收路线

C2C 是读取通路，冻结证据是验收输入规则，二者可同时使用。C2C Project 审核可读已授权精确快照；当前连接无法直读的已授权冻结原件可由 Codex 先核 `workspace_info` 后通过原生附件补充（本轮全局/ChatGPT 设置文件在 C2C 根外）。附件上传、完整度和记录边界同样适用。普通规划仍遵守仅 MCP 正文读取规则，不向普通消息粘代码或日志，不新增数据权限。

使用前必须由 Codex 从池中选择一个当前可用 Project，并用当前可用工具核实其身份、当前独占和一次一单；每个并行独立验收使用不同的 project-only Project、新 Chat 和精确候选，核实上轮聊天和业务材料已移出，并固定精确快照。当前会话、Project、role 记录或候选 SHA 只能证明相应可观察事实，不能单独机器证明项目记忆、上下文或硬只读隔离；只有可观察证据共同满足时才称独立验收，否则 fail-closed 为普通复核或“独立审核未完成”。audit 初次持久绑定必须回读完整 Project-chat URL、精确匹配 Project 身份、同一 connector 和精确候选 SHA；planning 初次绑定也必须回读完整 Project-chat URL、精确匹配 Project 身份和同一 connector。已有完整绑定后，task、title 或 checkpoint 可按支持字段部分更新；读回不完整的已有记录必须 fail-closed，不得冒称可用或自动回退 legacy。audit task 或 iteration 变化时必须显式确认候选；同候选状态更新可沿用未变化的 candidate。若 URL 或 Project 改变且存在旧 checkpoint，必须先经维护入口显式清除 checkpoint 再重绑，不能暗继承。完成后先将完整记录保存到各源项目认可存储，再核实移出完成会话和业务材料并归档，Project 才可复用；不自动永久删除，不累积跨项目审计记忆，不假称池分配由软件自动实现。池无可核验空位，或任一独占、清理、隔离状态无法核实，立即改走上面的临时附件路线，不强制排队。

池占用门：开始 UI 占用前，使用实际 C2C state 目录中的索引和 `audit-project-leases/<真实 Project ID>.json`，以 `create-exclusive/wx` 原子创建 lease，先记录完整 owner、task、`auditRun`、`stage=preparing`，发送验收前再补精确 candidate。已有他人 lease 时不抢占、不按超时猜闲置；同 owner 恢复也必须核对实际任务。完整留证与清理回读完成后先核对 owner，再释放 lease。索引只用于定位，不是空闲证明；跨机器不能依赖本机 lease 证明独占，无法证明时使用新的隔离环境。

当前维护入口 `node "<ACTUAL_CHECKOUT_PATH>/dist/cli/index.js" session ... --role ...` 只支持持久 C2C Project 路线；`--candidate` 在 audit 初次绑定以及任务/轮次变更时必填；同一候选的其他状态更新可沿用。它只是候选 SHA 元数据，不证明文件已验收或硬隔离，也不记录 PASS，临时附件 Chat 不得写入该 role。普通 Doctor、连接和旧命令继续使用 `node "<ACTUAL_CHECKOUT_PATH>/bin/c2c.js"`；本专项不升级 active-version、健康 Bridge 或安装运行时。不得猜测未实现的自动 API、沙箱、持久后台能力或导出能力。

当前每个工作区与完整 Codex owner 只有一个 audit 角色记录。同一组合已有活跃验收时，另一并行审核不得覆盖它；采用临时附件及独立 auditRun 留证作为补位，不阻塞其他任务。完成且移出会话后，原 DONE 记录仅用于历史定位，不证明会话仍在该 Project；下一单须新建会话、重新核验并绑定新候选。

维护入口须已构建并核验源版本；源码改变后先完成受影响验证和构建，未变的有效构建证据可复用，不把源码已保存当作编译入口已更新。

当 `--role planning` 已绑定时，规划消息、恢复和检查点优先使用该 owner 的绑定，不回退到 legacy `--same-thread` 覆盖；没有 role 文件的 legacy 会话继续按原兼容路径处理。已授权的冻结附件补证可与 C2C Project 读取通路并用，是黄金规则的窄例外：Project 补证前仍先核 `workspace_info`；临时不个性化模式不强制永久 `/c/`，附件上传、完整度和记录边界同样适用；普通规划仍遵守仅 MCP 正文读取规则，不向普通消息粘代码或日志，不新增数据权限。其余 C2C Doctor、连接器、发送保护、等待和权限边界全部保持不变。
